# Node Discovery Protocol v5 - Theory

**Protocol version v5.1**

This document explains the algorithms and data structures used by the protocol.

## Nodes, Records and Distances

A participant in the Node Discovery Protocol is represented by a 'node record' as defined in [EIP-778].
The node record keeps arbitrary information about the node. For the purposes of this protocol, the node
must at least provide an IP address (`"ip"` or `"ip6"` key) and UDP port (`"udp"` key) in order to have
it's record relayed in the DHT.

Node records are signed according to an 'identity scheme'. Any scheme can be used with Node Discovery
Protocol, and nodes using different schemes can communicate. The identity scheme of a node record defines
how a 32-byte 'node ID' is derived from the information contained in the record.

The 'distance' between two node IDs is the bitwise XOR of the IDs, taken as the big-endian number.

    distance(n₁, n₂) = n₁ XOR n₂

In many situations, the logarithmic distance (i.e. length of differing suffix in bits) is used in place of the
actual distance.

    logdistance(n₁, n₂) = log2(distance(n₁, n₂))

### Maintaining The Local Node Record

Participants should update their record, increase the sequence number and sign a new version of the record
whenever their information changes. This is especially important for changes to the node's IP address and port.

Implementations should determine the external endpoint (the Internet-facing IP address and port on which
the node can be reached) and include it in their record. If communication flows through a NAT device, the
UPnP/NAT-PMP protocols or the mirrored UDP envelope IP and port found in the [PONG] message can be used
to determine the external IP address and port. If the endpoint cannot be determined (e.g. when the NAT
doesn't support 'full-cone' translation), implementations should omit IP address and UDP port from the record.

## Sessions

Discovery communication is encrypted and authenticated using session keys, established in the handshake.
Since every node participating in the network acts as both client and server, a handshake can be initiated
by either side of communication at any time.

### Handshake Steps

#### Step 1: Node A sends message packet

In the following definitions, we assume that node A wishes to communicate with node B, e.g. to send a
FINDNODE message. Node A must have a copy of node B's record in order to communicate with it.

If node A has session keys from prior communication with B, it encrypts its request with those keys.
If no keys are known, it initiates the handshake by sending an ordinary message packet with random
message content.

    A -> B    FINDNODE message packet encrypted with unknown key

#### Step 2: Node B responds with challenge

Node B receives the message packet and extracts the source node ID from the packet header. If node B has
session keys from prior communication with A, it attempts to decrypt the message data. If decryption and
authentication of the message succeeds, there is no need for a handshake and node B can simply respond to
the request.

If node B does not have session keys or decryption is not successful, it must initiate a handshake by
responding with a [WHOAREYOU packet]. It first generates a unique `id-nonce` value and includes it in the
packet. Node B also checks if it has a copy of node A's record. If it does, it also includes the sequence
number of this record in the challenge packet, otherwise it sets the `enr-seq` field to zero.

Node B must also store the A's record and the WHOAREYOU challenge for a short duration after sending it to
node A because they will be needed again in step 4.

    A <- B    WHOAREYOU packet including id-nonce, enr-seq

#### Step 3: Node A processes the challenge

Node A receives the challenge sent by node B, which confirms that node B is alive and is ready to perform
the handshake. The challenge can be traced back to the request packet which solicited it by checking the
`nonce`, which mirrors the request packet's `nonce`.

Node A proceeds with the handshake by re-sending the FINDNODE request as a [handshake message packet].
This packet contains three parts in addition to the message: `id-signature`, `ephemeral-pubkey` and `record`.

The handshake uses the unmasked WHOAREYOU challenge as an input:

    challenge-data = masking-iv || static-header || authdata

Node A can now derive the new session keys. To do so, it first generates an ephemeral key pair on the
elliptic curve used by node B's identity scheme. As an example, let's assume the node record of B uses the
"v4" scheme. In this case the `ephemeral-pubkey` will be a public key on the secp256k1 curve.

    ephemeral-key = random private key generated by node A
    ephemeral-pubkey = public key corresponding to ephemeral-key

The ephemeral key is used to perform Diffie-Hellman key agreement with node B's static public key and the
session keys are derived from it using the HKDF key derivation function.

    dest-pubkey        = public key corresponding to node B's static private key
    secret             = ecdh(dest-pubkey, ephemeral-key)
    kdf-info           = "discovery v5 key agreement" || node-id-A || node-id-B
    prk                = HKDF-Extract(challenge-data, secret)
    key-data           = HKDF-Expand(prk, kdf-info)
    initiator-key      = key-data[:16]
    recipient-key      = key-data[16:]

Here `HKDF-Extract(salt, IKM)` and `HKDF-Expand` are the functions defined in [RFC 5869]
using HMAC-SHA-256. The salt is `challenge-data` and the input keying material is `secret`;
`HKDF-Expand` is invoked with `kdf-info` and produces 32 bytes of output.

Node A creates the `id-signature`, which proves that it controls the private key which
signed its node record. The signature also prevents replay of the handshake.

    id-signature-text = "discovery v5 identity proof"
    id-signature-input = id-signature-text || challenge-data || ephemeral-pubkey || node-id-B
    id-signature = id_sign(sha256(id-signature-input))

Finally, node A compares the `enr-seq` element of the WHOAREYOU challenge against its own node record
sequence number. If the sequence number in the challenge is lower, it includes its record into the handshake
message packet. The request is now re-sent, with the message encrypted using the new session keys.

    A -> B    FINDNODE handshake message packet, encrypted with new initiator-key

#### Step 4: Node B receives handshake message

When node B receives the handshake message packet, it first loads the node record and WHOAREYOU challenge
which it sent and stored earlier. If node B did not have the node record of node A, the handshake message
packet must contain a node record. A record may also be present if node A determined that its record is
newer than B's current copy. If the packet contains a node record, B must first validate it by checking the
record's signature.

Node B then verifies the `id-signature` against the identity public key of A's record. After that, B can
perform the key derivation using its own static private key and the `ephemeral-pubkey` from the handshake
packet. Using the resulting session keys, it attempts to decrypt the message contained in the packet.

If the message can be decrypted and authenticated, Node B considers the new session keys valid and responds
to the message. In our example case, the response is a `NODES` message:

    A <- B    NODES encrypted with new recipient-key

#### Step 5: Node A receives response message

Node A receives the message packet response and authenticates/decrypts it with the new session keys. If
decryption/authentication succeeds, node B's identity is verified and node A also considers the new session
keys valid.

### Identity-Specific Cryptography in the Handshake

Establishment of session keys is dependent on the [identity scheme] used by the recipient (i.e. the node
which sends WHOAREYOU). Likewise, the signature over `id-sig-input` is made by the identity key of the
initiator. It is not required that initiator and recipient use the same identity scheme in their respective
node records. Implementations must be able to perform the handshake for all supported identity schemes.

At this time, the only supported identity scheme is "v4". `id_sign(hash)` creates a signature over `hash`
using the node's static private key. The signature is encoded as the 64-byte array `r || s`, i.e. as the
concatenation of the signature values. `ecdh(pubkey, privkey)` creates a secret through elliptic-curve
Diffie-Hellman key agreement. The public key is multiplied by the private key to create a secret ephemeral
key `eph = pubkey * privkey`. The 33-byte secret output is `y || eph.x` where `y` is `0x02` when `eph.y`
is even or `0x03` when `eph.y` is odd.

### Handshake Implementation Considerations

Since a handshake may happen at any time, UDP packets may be reordered by transmitting networking equipment,
implementations must deal with certain subtleties regarding the handshake.

In general, implementations should keep a reference to all sent request packets until the request either
times out, is answered by the corresponding response packet or answered by WHOAREYOU. If WHOAREYOU is
received as the answer to a request, the request must be re-sent as a handshake packet.

If an implementation supports sending concurrent requests, multiple responses may be pending when WHOAREYOU
is received, as in the following example:

    A -> B    FINDNODE
    A -> B    PING
    A -> B    TOPICQUERY
    A <- B    WHOAREYOU (nonce references PING)

When this happens, all buffered requests can be considered invalid (the remote end cannot decrypt them) and
the packet referenced by the WHOAREYOU `nonce` (in this example: PING) must be re-sent as a handshake. When
the response to the re-sent is received, the new session is established and other pending requests (example:
FINDNODE, TOPICQUERY) may be re-sent. Note that WHOAREYOU is only ever valid as a response to a previously
sent request. If WHOAREYOU is received but no requests are pending, the handshake attempt can be ignored.

Another important issue is the processing of message packets while a challenge is received: consider the case
where node A has sent a packet that B cannot decrypt, and B has responded with WHOAREYOU.

    A -> B    FINDNODE
    A <- B    WHOAREYOU

Node B is now waiting for a handshake message packet to complete the new session, but instead receives
another ordinary message packet.

    A -> B    ORDINARY MESSAGE PACKET

In this case, implementations should respond with a new WHOAREYOU challenge referencing the message packet.

### Session Cache

Nodes should store session keys for communication with other recently-seen nodes. Since sessions are ephemeral
and can be re-established whenever necessary, it is sufficient to store a limited number of sessions in an
in-memory LRU cache. To prevent IP spoofing attacks, implementations must ensure that session secrets and the
handshake are tied to a specific UDP endpoint. This is simple to implement by using the node ID and IP/port as
the 'key' into the in-memory session cache.

When a node switches endpoints, e.g. when roaming between different wireless networks, sessions will have to
be re-established by handshaking again. This requires no effort on behalf of the roaming node because the
recipients of protocol messages will simply refuse to decrypt messages from the new endpoint and reply with
WHOAREYOU.

The number of messages which can be encrypted with a certain session key is limited because encryption of each
message requires a unique nonce for AES-GCM. In addition to the keys, the session cache must also keep track
of the count of outgoing messages to ensure the uniqueness of nonce values. Since the wire protocol uses 96 bit
AES-GCM nonces, it is strongly recommended to generate them by encoding the current outgoing message count into
the first 32 bits of the nonce and filling the remaining 64 bits with random data generated by a cryptographically
secure random number generator.

## Node Table

Nodes keep information about other nodes in their neighborhood. Neighbor nodes are stored in a routing table
consisting of 'k-buckets'. For each `0 ≤ i < 256`, every node keeps a k-bucket for nodes of
`logdistance(self, n) == i`. The Node Discovery Protocol uses `k = 16`, i.e. every k-bucket contains up to
16 node entries. The entries are sorted by time last seen — least-recently seen node at the head,
most-recently seen at the tail.

Whenever a new node N₁ is encountered, it can be inserted into the corresponding bucket. If the bucket contains
less than `k` entries N₁ can simply be added as the first entry. If the bucket already contains `k` entries, the
liveness of the least recently seen node in the bucket, N₂, needs to be revalidated. If no reply is received from
N₂ it is considered dead, removed and N₁ added to the front of the bucket.

Neighbors of very low distance are unlikely to occur in practice. Implementations may omit k-buckets for low
distances.

### Table Maintenance In Practice

Nodes are expected to keep track of their close neighbors and regularly refresh their information. To do so,
a lookup targeting the least recently refreshed bucket should be performed at regular intervals.

Checking node liveness whenever a node is to be added to a bucket is impractical and creates a DoS vector.
Implementations should perform liveness checks asynchronously with bucket addition and occasionally verify that
a random node in a random bucket is live by sending [PING]. When the PONG response indicates that a new version
of the node record is available, the liveness check should pull the new record and update it in the local table.
If a node's liveness has been verified many times, implementations may consider occasional non-responsiveness
permissible and assume the node is live.

When responding to FINDNODE, implementations must avoid relaying any nodes whose liveness has not been verified.
This is easy to achieve by storing an additional flag per node in the table, tracking whether the node has ever
successfully responded to a PING request.

In order to keep all k-bucket positions occupied even when bucket members fail liveness checks, it is strongly
recommended to maintain a 'replacement cache' alongside each bucket. This cache holds recently-seen nodes which
would fall into the corresponding bucket but cannot become a member of the bucket because it is already at capacity.
Once a bucket member becomes unresponsive, a replacement can be chosen from the cache.

### Lookup

A 'lookup' locates the `k` closest nodes to a node ID. The lookup initiator starts by picking `α` closest nodes
to the target it knows of from the local table. The initiator then sends [FINDNODE] requests to those nodes.

`α` is an implementation-defined concurrency parameter, typically `3`. As NODES responses are received, the
initiator resends FINDNODE to nodes it has learned about from previous queries. Of the `k` nodes the initiator
has heard of closest to the target, it picks `α` that it has not yet queried and sends FINDNODE to them. The
lookup terminates when the initiator has queried and gotten responses from the `k` closest nodes it has seen.

To improve the resilience of lookups against adversarial nodes, the algorithm may be adapted to perform network
traversal on multiple disjoint paths. Not only does this approach benefit security, it also improves effectiveness
because more nodes are visited during a single lookup.

The initial `k` closest nodes are partitioned into multiple independent 'path' buckets, and concurrent FINDNODE
requests executed as described above, with one difference: results discovered on one path are not reused on another,
i.e. each path attempts to reach the closest nodes to the lookup target independently without reusing intermediate
results found on another path. Note that it is still necessary to track previously asked nodes across all paths to
keep the paths disjoint.

### Lookup Protocol

This section shows how the wire protocol messages can be used to perform a lookup interaction against a single node.

Node `A` is looking for target `x`. It selects node `B` from the local table or intermediate lookup results.
To query for nodes close to `x` on `B`, node `A` computes the query distance `d = logdistance(B, x)` and sends
its request.

    A -> B    FINDNODE [d]

Node `B` responds with multiple nodes messages containing the nodes at the queried distance.

    A <- B    NODES [N₁, N₂, N₃]
    A <- B    NODES [N₄, N₅]

Depending on the value of `d` and the content of `B`s table, the response to the initial query might contain very
few nodes or no nodes at all. Should this be the case, `A` varies the distance to retrieve more nodes from adjacent
k-buckets on `B`:

    A -> B    FINDNODE [d+1]

`B` responds with more nodes:

    A <- B    NODES [N₆, N₇]

Node `A` now sorts all received nodes by distance to the lookup target and proceeds by repeating the lookup
procedure on another, closer node.

# Topic-based Service Discovery

Topic-based discovery (**TopDisc**), referred to as **DISC-NG** in the accompanying academic paper [DISC-NG paper], extends Discovery v5 with a mechanism to discover nodes according to their provided services (topics). Nodes advertise participation in a service through registration operations, and other nodes discover those advertisements through lookup operations, while reusing the existing Node Table and ENR mechanisms.

## Co-existence with Node Discovery

The TopDisc system builds on the basic routing of discv5. A TopDisc-capable node first
joins the network using [FINDNODE] and populates its local node table, learning about
TopDisc-capable nodes. These nodes are then used to bootstrap service tables (see below).
As registration and lookup operations proceed, TopDisc-capable nodes can also return
additional nodes to improve the service tables, as described below.

Failure of a TopDisc registration or lookup request does not by itself imply an ordinary
Discovery v5 failure. A node may remain usable for ordinary node discovery even if it is
temporarily unusable for TopDisc registration or lookup. Conversely, a node that
fails ordinary Discovery v5 liveness checks ceases to be eligible for insertion into TopDisc service
tables.

## ENR Capability

A node indicates support for service discovery messages by including the [ng ENR entry] in its ENR.

    ng = <version>

The value of `ng` is an unsigned integer identifying the supported TopDisc protocol
version. Nodes whose ENR does not contain `ng`, or whose `ng` value is not supported by
the local implementation are not inserted into service tables and are not selected for
registration or lookup requests.

## Services and Service Identifiers

TopDisc operates on 32-byte service identifiers. A service identifier represents a higher-level
service, subnetwork, overlay, or other application-specific discovery target.

Service identifiers are in the same 256-bit (32-byte) identifier space as Node IDs. This allows TopDisc to
apply the Node Discovery v5 XOR distance function between service identifiers and node IDs.

Applications identify a service using a string. This string is hashed to obtain the 32-byte
service identifier:

    s = H(service-string)

The application chooses the service string. It may encode information such as a protocol name,
network name, fork identifier, capability, subnet identifier, or a combination of such values.
Nodes referring to the same service must use the same string so that they derive the same
service identifier.

Once derived, the service identifier is treated as an opaque 32-byte value by the TopDisc
registration and lookup procedures.

## Node Roles

A node that advertises `ng` capability in its ENR acts as a registrar, subject to local policy
and resource limits.

A **registrar** accepts registration and lookup requests, admits advertisements into its
local **ad cache**, and returns admitted advertisements to discoverers.

A TopDisc-capable node may also act as an advertiser, a discoverer, or both.

An **advertiser** participates in a service and registers advertisements for that service with
registrars. A node acts as an advertiser only for services that it chooses to advertise.

A **discoverer** queries registrars to obtain advertisements for a target service. A node acts as a
discoverer only when it is looking up peers for a service.

The roles are not mutually exclusive. A single node can simultaneously act as a registrar, advertise
one or more services, and discover peers for one or more services.

## Service Tables

A service table `B(s)` is a per-service node table centred on service identifier `s`, rather than on
the local node ID.

Similar to the ordinary Node Table, `B(s)` is divided into distance buckets. The difference is the
reference point used to assign nodes to buckets. In the ordinary node table, a node `n` is placed
according to `logdistance(self, n)`, where `self` is the local node ID. In a service table, the same
node `n` is placed according to `logdistance(s, n)`, where `s` is the service identifier.

Service-table buckets are assigned according to `logdistance(s, n)`. For distinct identifiers,
this distance ranges from `1` to `256`, with larger values denoting nodes farther from `s`.

For a logarithmic distance `i`:

    bᵢ(s) = { n | logdistance(s, n) = i }

Thus, `B(s)` gives the local node a service-centred view of the discovery network. Buckets closer
to `s` contain nodes whose IDs are closer to the service identifier, while buckets farther from
`s` contain nodes from progressively larger regions of the key space.

A node may maintain a service table for each service identifier for which it performs TopDisc
operations. Advertisers use `B(s)` as an advertise table for service `s`; discoverers use `B(s)` as
a search table for service `s`.

Whether a node that both advertises and searches for `s` keeps one table or two is an
implementation choice. The current implementation keeps two: an advertise table kept for as long as
`s` is advertised, and a search table filled afresh for each search pass. The topic-distance hints
of a request come from the table of the operation that sends it: [REGTOPIC] lists the advertise
buckets with space (see [Advertisement Placement](#advertisement-placement)), [TOPICQUERY] the
search buckets around the active bucket (see
[Updating the Search Table During Lookup](#updating-the-search-table-during-lookup)).

### Bootstrapping from Ordinary Node Discovery

A node does not start advertisement placement or lookup from an empty service table.

The node first joins the Node Discovery v5 network using the standard bootstrapping procedure. It
populates its ordinary local node table through the existing `PING`, `PONG`, `FINDNODE`, lookup,
refresh, and liveness mechanisms.

For a service identifier `s`, the initial service table `B(s)` is derived from the ordinary
node table. When constructing this initial service table, implementations should:

1. take nodes currently known in the ordinary node table;
2. discard nodes whose ENR does not advertise a supported TopDisc version;
3. discard nodes whose liveness has not been verified by the ordinary Node Discovery v5 table-maintenance rules;
4. discard nodes currently excluded by local TopDisc usability policy;
5. insert each remaining node into the corresponding bucket of `B(s)`.

The resulting `B(s)` is soft state. It need not be complete before operations begin. If the
ordinary node table contains too few nodes that can be used for operations, implementations
should continue ordinary Node Discovery v5 refresh and lookup operations until more candidates are
learned.

### Ongoing Maintenance of `B(s)`

A service table is maintained from two sources:

1. the ordinary Discovery v5 node table; and
2. auxiliary ENRs learned through registration and lookup responses.

When a newly verified node advertising TopDisc capability is learned through ordinary discovery,
it becomes eligible for insertion into relevant service tables.

Responses to registration and lookup requests may include auxiliary ENRs selected according to
[Auxiliary ENR Selection](#auxiliary-enr-selection). Such ENRs may be inserted into `B(s)` only
after ENR validation, capability checking, and any local usability checks.

### Auxiliary ENR Selection

Auxiliary ENRs are routing information used by the
requester to improve its local service table `B(s)`; they are not service lookup results.

A request may carry a list of topic-distances at which the requester's service table has free space.
A topic-distance is a logarithmic distance from the service identifier `s` to a node ID, and
therefore identifies a bucket of `B(s)`.

When such a list is present, the registrar SHOULD use it as a hint for auxiliary ENR selection. For
each requested topic-distance `d`, the registrar SHOULD return at most one ENR for a TopDisc-capable
node `n` such that:

    logdistance(s, n) = d

The registrar may obtain such ENRs from any local source of known TopDisc-capable nodes, including
an existing service table `B(s)`, the ordinary node table filtered to TopDisc-capable nodes, or an
implementation-local cache. A registrar is not required to maintain a service table for every
service represented in its ad cache.

A recommended selection algorithm is:

1. iterate over the topic-distances supplied by the requester;
2. for each distance `d`, select at most one known TopDisc-capable node whose node ID satisfies
   `logdistance(s, n) = d`;
3. prefer pseudo-random selection when multiple eligible ENRs are available for the same distance;
4. skip ENRs that fail local validation or usability checks;
5. stop when all requested distances have been considered or when an implementation-defined cap on
   auxiliary ENRs has been reached.

Selecting at most one ENR per requested distance keeps responses compact and spreads coverage across
the requester's free buckets. It avoids overrepresenting a single distance and reduces the ability
of a responder to fill a response with many ENRs from one bucket.

If the registrar has no eligible ENR for a requested distance, it omits that auxiliary ENR.

The requester lists the topic-distances in priority order, and a registrar that caps auxiliary
ENRs serves the earliest listed distances first. The current implementation serves at most the
first 8 listed distances, so it returns at most 8 auxiliary ENRs. It draws them from its ordinary
node table, keeping TopDisc-capable nodes whose address may be relayed to the requester, as for
[NODES] responses to [FINDNODE], and picks one at random per distance. Unlike [FINDNODE] responses,
these ENRs are not restricted to nodes whose liveness the registrar has verified. An advertiser
lists the distances of its advertise buckets from farthest to closest, and gives the closest
bucket, which holds all distances `239` and below, as distance `239`.

The same auxiliary-ENR selection rule applies to registration responses and lookup responses.

### TopDisc Liveness and Temporary Exclusion

A node advertising TopDisc capability is not automatically a usable registrar for every TopDisc
operation. It may time out, return malformed responses, reject requests, or fail to implement the
extension correctly.

Implementations should therefore maintain TopDisc-level usability state for nodes in `B(s)`.

If a node in `B(s)` repeatedly fails to answer registration or lookup requests, times out, or
returns malformed responses, implementations should temporarily exclude that node from selection for
operations. Temporary exclusion may be implemented by removing the node from `B(s)`,
suppressing its selection for a backoff period, or assigning it lower selection priority.

Temporary exclusion is not a permanent blacklist. After the backoff period expires, the node may
become eligible for re-insertion into `B(s)` if it is still present in the ordinary node table,
still advertises TopDisc capability, and still satisfies ordinary Discovery v5 liveness
requirements.

Failure of a request does not by itself require removal from the ordinary Discovery v5
node table. Retention in the ordinary node table continues to follow Discovery v5 liveness
and table-maintenance rules.

## Registrar Behaviour

### Ad Cache

A registrar stores admitted advertisements in a bounded ad cache.

Each admitted advertisement expires after duration `E`. The ad cache has capacity `C`, a hard
limit: a registrar MUST NOT hold more than `C` advertisements. A registrar stores at most one
active advertisement for the same advertiser and service.

When an advertisement has waited long enough to be admitted but the cache is full, the registrar
returns a ticket whose waiting time is the time until the next advertisement in the cache
expires. The advertiser retries at that time with the ticket, and keeps the waiting time it has
accumulated. The time until the next expiry can be below `W_min`; the advertiser then waits
`W_min` (see [Registration Procedure](#registration-procedure)).

The ad cache is not a service table. It is registrar-local storage used to answer service lookup
requests.

An ad cache entry contains at least:

- the service identifier;
- the advertiser ENR;
- the expiry time;
- any advertisement payload defined by the service binding or wire-format document.

Implementations may maintain additional indices for efficient retrieval by service, expiry time,
advertiser, and IP prefix.

Expired advertisements are removed automatically. Once an advertisement expires, it is no longer
returned in lookup responses.

A registrar SHOULD also remove an advertiser's advertisements, for all services, when its ordinary
node table drops the advertiser after failed liveness checks. Discoverers would otherwise be sent
to a node that the registrar itself no longer considers alive. Advertisements of an advertiser that
is not in the node table are kept until they expire.

The registrar MUST NOT store duplicate active advertisements for the same advertiser and service.
The current implementation answers a registration request for an advertisement already in the
cache as admitted, with `wait-time` equal to `E`, and leaves the stored advertisement and its
expiry time unchanged. Re-registering before expiry therefore does not extend an advertisement.
Open issue: the reported lifetime can exceed the remaining one, so the advertiser may count the
advertisement as active after it has expired. Reporting the remaining lifetime would remove this
mismatch.

### Advertisements

An advertisement states that the node identified by an ENR participates in a service/topic.

An advertisement is defined as:

    ad = [topic, ENR]

where:

- `topic` is the 32-byte service/topic identifier;
- `ENR` is the advertised node record.

The advertisement digest is:

    ad-digest = H(ad)

where `H` is the digest function used by the admission-control mechanism to bind registration
tickets to advertisements. The admission-control and ticket mechanisms are described below.

If future versions allow service-specific advertisement payloads, the advertisement definition
becomes:

    ad = [topic, ENR, payload]

### Admission Control

Registrars use admission control to decide whether and when an incoming registration request for an
advertisement may be admitted to the ad cache.

Admission is based on a **waiting-time mechanism**. If an advertisement is not admitted immediately,
the registrar returns a ticket and a waiting time. This mechanism promotes diversity in the ad cache
and avoids requiring registrars to keep unbounded per-request state for pending registrations.

Before computing a waiting time, the registrar checks the advertised ENR. It MUST reject the request
if the ENR is invalid, if its node ID is not the sender's, if its address of the packet's address
family does not equal the packet's source address, or if its address of the other family is not
publicly routable (see [REGTOPIC]). A rejection is answered with a [REGCONFIRMATION] carrying no
ticket and a waiting time of `0`, and no auxiliary ENRs.

When a registrar receives a registration request, it computes a waiting time from the current state
of the ad cache and the incoming advertisement. If the effective remaining waiting time is at most
`W_min`, the minimum quoted waiting time, the advertisement is admitted. Otherwise, the registrar
returns a ticket and the remaining waiting time; `W_min = 1 sec`. The slack admits an advertiser
whose remaining wait is too short to be worth another round trip, so a registrar SHOULD NOT quote
a waiting time below `W_min`. Two replies can still carry a shorter one: the next-expiry reply of a
full cache (see [Ad Cache](#ad-cache)) and an early ticket returned unchanged (see
[Tickets](#tickets)). Advertisers MUST tolerate such quotes as described in
[Registration Procedure](#registration-procedure).

The registrar does not need to keep per-request state for pending registrations. Instead, the state
needed to prove accumulated waiting time is carried by the advertiser in the registrar-issued
ticket.

The waiting time in a ticket is not binding. On each retry, the registrar recomputes the waiting
time using the current ad cache state. The advertiser is admitted only when its accumulated waiting
time is sufficient according to the recomputed waiting time.

Every registration request is answered. If an advertiser retries too early, the registrar returns
its ticket unchanged with the remaining wait. If it retries too late, omits the latest ticket,
presents a ticket that was already credited, or presents an invalid ticket, the registrar treats
the request as a new registration attempt. The rules are given in [Tickets](#tickets).

### Tickets

A ticket is a registrar-issued, registrar-authenticated object that allows an advertiser to retry a
registration attempt after waiting.

A ticket is bound to a specific advertisement and registrar. The advertisement is denoted `ad` and
includes the service identifier, the advertised ENR, and any service-specific advertisement payload.
The ticket contains a digest of this advertisement, denoted `adDigest`.

The advertiser uses the latest ticket issued by the registrar when retrying the registration. A
ticket issued for one advertisement or registrar MUST NOT be accepted for a different registration
request. In particular, a ticket issued for one service, advertised ENR, or advertisement payload
MUST NOT be reused for another. The current implementation binds a ticket to the service identifier
only, not to the advertiser (datahop/go-ethereum#68); see
[Security Considerations](./discv5-rationale.md#topdisc-security-considerations).

The ticket is opaque to the advertiser. The advertiser does not interpret the ticket contents; it
stores the latest ticket returned by the registrar and presents it in the next registration attempt
to the same registrar. The exact ticket encoding, digest function, authentication mechanism,
signature format, and signature domain are specified in the wire-format document.

Algorithmically, a ticket contains enough authenticated information for the registrar to verify:

- `adDigest`: the digest of the advertisement to which the ticket applies;
- `tinit`: the registrar-local time at which the ticket was first issued;
- `tmod`: the registrar-local time at which the ticket was last modified;
- `twait`: the remaining waiting duration reported to the advertiser;
- `auth`: registrar authentication over the ticket contents.

The registrar authenticates the ticket, for example by signing the ticket body or applying a
registrar-local MAC. A registrar MUST reject a ticket that fails authentication, that was not
issued by that registrar, or that was issued for a different advertisement: it credits no waiting
time for it and treats the request as a new registration attempt, which it still answers.

The timestamps `tinit` and `tmod` are generated and interpreted only by the registrar. They are
local to the registrar and are not compared against the advertiser's clock. The only timing value
used by the advertiser is the relative waiting duration `twait` reported by the registrar in the
registration response.

A retry is valid only during the registration window associated with the ticket:

    tmod + twait ≤ now < tmod + twait + δ

where `now` is the registrar's current local time when processing the retry, and `δ` is the
registration window duration, `δ = 5 sec`.

The advertiser does not use `tmod` to schedule the retry and does not need its clock to be
synchronised with the registrar's clock. The advertiser waits for the relative duration `twait`
using its own local timer, then retries with the latest ticket. The registrar validates the retry
window using its own clock when the ticket is presented again.

When a returning advertiser presents a valid ticket within its window, the registrar computes the
accumulated waiting duration as:

    waited = now - tinit

where `now` and `tinit` are both interpreted according to the registrar's local clock.

The registrar answers every retry with a [REGCONFIRMATION]. Let `start = tmod + twait` be the
start of the ticket's window and `ε` the late grace, a registrar-local duration that MUST be small
against `E`; the recommended value is `ε = 10 sec`. The registrar treats an authenticated ticket
according to when it is presented:

- **Early** (`now < start`): the registrar returns the same ticket bytes it received, with
  `start - now` as the waiting time, and no auxiliary ENRs. It does not evaluate the
  waiting-time function and does not move the window. An early retry can neither shorten the wait
  nor learn the current waiting time.
- **On time** (`start ≤ now < start + δ`): the ticket is credited with `waited = now - tinit`.
- **Late** (`start + δ ≤ now < start + δ + ε`): the ticket is credited with the waiting time it
  was scheduled to have, `waited = start - tinit`. If the registrar issues a new ticket in reply,
  it sets that ticket's `tinit` to `now - waited`, so that the time past the window is not
  credited on the next retry either.
- **Expired** (`now ≥ start + δ + ε`): the ticket proves nothing. The request is a new
  registration attempt (`waited = 0`, `tinit = now`).

A ticket is credited once. A registrar that has credited a ticket, on time or late, MUST treat any
later presentation of the same ticket as a new registration attempt, and still answer it. To do
so, it MUST remember each credited ticket for at least `δ + ε` after the ticket's window start,
the span in which the ticket could be credited. Whoever presents a ticket first consumes it. The
current implementation remembers credited tickets by their MAC for `δ + ε` from the time of
crediting, up to 16,384 entries, dropping the oldest entry when full.

A retry that does not include the latest ticket, or whose ticket fails authentication or belongs to
another advertisement, is a new registration attempt.

Because the ticket is bound to `adDigest`, changing the service identifier, advertised ENR, or
service-specific advertisement payload during a registration attempt requires starting a new
registration attempt or obtaining a new ticket for the updated advertisement.

### Waiting-Time Function

The waiting-time function determines how long an advertisement must wait before admission.

The function depends on the current ad cache occupancy, the number of cached advertisements for the
same service, and the IP similarity of the advertiser. The waiting time shapes the contents of the
ad cache and provides flow control at the registrar. The function is registrar-local: an advertiser
only follows the waiting times it is given. The recommended function, as currently implemented
(provisional, see [Parameters](#parameters)), is:

    base(c) = Wbase * E / (1 - c/C)^Pocc
    w(ad)   = base(c) * c(ad.service) / (c + 1)  +  base(c) * score(ad.IP)

where:

- `E` is the advertisement expiry duration;
- `C` is the ad cache capacity;
- `c` is the current number of advertisements in the cache;
- `c(ad.service)` is the number of cached advertisements for the service being advertised;
- `score(ad.IP)` is the IP similarity score computed from the advertiser's IP (ad.IP) in the
  advertised ENR;
- `Pocc` is the occupancy exponent;
- `Wbase` is the base waiting-time factor, `0.1`, so that `base(0) = E / 10`.

The first term is the service component and the second the IP component. Each component is raised
to its lower bound before the two are added (see [Waiting-Time Lower Bound](#waiting-time-lower-bound)).

`base(c)` grows without bound as `c` approaches `C`. The registrar caps the resulting waiting time,
and every recorded lower bound, at `maxWaitTime` before converting it to its local duration type.
The recommended value is `maxWaitTime = 24 h` (provisional), far above any attempt budget, so a
capped quote still makes the advertiser abandon the attempt (see
[Registration Procedure](#registration-procedure)).

This differs from the form given in [DISC-NG paper], `E / (1 - c/C)^Pocc * (c(ad.service)/c +
score(ad.IP) + G)`, in three ways: the occupancy factor is scaled by `Wbase`, the service term
divides by `c + 1`, which also defines it for an empty cache, and there is no safety constant
`G`. The reasons are given in the
[rationale](./discv5-rationale.md#why-change-the-waiting-time-function).

The occupancy component increases the waiting time as the ad cache approaches capacity. This limits
the rate at which new advertisements can be admitted.

The service-similarity component increases the waiting time for services that are already well
represented in the cache. This makes it easier for less represented services to obtain cache
entries.

The IP-similarity component increases the waiting time for advertisers whose IP prefixes are
overrepresented in the cache. This discourages a small number of IP prefixes from dominating the
registrar's ad cache.

An advertisement for a service with no cached advertisements, from an address with a score of `0`
and no applicable lower bound, has a waiting time of `0` and is admitted at once if the cache has
space.

When a returning advertiser presents a valid ticket, the registrar computes the effective remaining
waiting time as:

    tremaining = w(current-cache, ad) - waited

where `waited` is the waiting time credited to the ticket (see [Tickets](#tickets)). The
advertisement is admitted when `tremaining ≤ W_min` and the cache has space.

### IP Similarity Tree

The IP similarity score `score(ad.IP)` used in the waiting-time function is computed
using an IP similarity tree. The tree measures whether an advertiser's IP address falls
within prefixes that are already overrepresented in the ad cache. A higher similarity
score therefore results in a higher registration waiting time.

Registrars maintain separate IP similarity trees for IPv4 and IPv6. Both trees
contain addresses from admitted advertisements across all services.

Each edge in an IP similarity tree corresponds to one bit of an IP address. Each vertex
represents an IP prefix and stores a counter indicating how many addresses are represented
by that prefix. The root counter gives the total number of addresses in the tree.

To score an address `x`, let `N` be the number of addresses in the corresponding tree.
The registrar examines progressively longer prefixes of `x`, walking down the tree starting from the root. For a prefix of length `k`,
an even distribution of the `N` addresses across the address space would give an expected
count of:

    N / 2^k

Only prefix lengths for which `2^k <= N` are considered, up to the maximum address
length. Let `D` be the number of prefix lengths considered.

For each considered prefix length `k`, let `c_k(x)` be the actual number of addresses
in the tree that share the first `k` bits of `x`. The prefix contributes one point to
the similarity score if its actual count is greater than the expected count:

    c_k(x) > N / 2^k

The final similarity score is the fraction of the `D` considered prefixes that
contribute a point:

    score(x) = number of points / D

If `D = 0`, the score is `0`. The score therefore lies in `[0, 1]`. A score closer to
`1` means that the address belongs to more prefixes that are overrepresented among
addresses already present in the ad cache.

IPv4 and IPv6 addresses are scored independently using their respective IP similarity
trees. If an advertisement contains eligible addresses from both families,
`score(ad.IP)` is the larger of the two scores. If only one eligible address family is
present, that family's score is used.

Loopback, private, and link-local addresses are not scored: they contribute `0`. The
IP similarity trees are updated as advertisements are admitted and removed. In the
current implementation, the addresses of admitted advertisements are inserted whether
or not they are scored, so such addresses still count towards `N`.

### Waiting-Time Lower Bound

Registrars enforce a lower bound on waiting times so that an advertiser cannot obtain a better
effective waiting time by repeatedly requesting new tickets.

Without a lower bound, a pending advertiser could repeatedly request new tickets in the hope that
cache changes cause a lower waiting time. The lower-bound rule ensures that a new waiting time
cannot improve on the old one by more than the elapsed time: for quotes `w1` at time `t1` and `w2`
at a later time `t2`, `w1 - w2 ≤ t2 - t1`.

Registrars do not maintain unbounded per-request lower-bound state for pending registrations.
Lower-bound state is maintained only for bounded structures, such as:

- services already represented in the ad cache; and
- prefixes represented in the IP similarity tree.

A lower bound records a value `v` and the time `t` at which it was recorded. At time `now` its
remaining value is `max(0, v - (now - t))`: it decays one second per second. When the registrar
issues a ticket, it raises each bound to the component it just computed, if that component exceeds
the bound's remaining value. Admissions do not change the bounds.

For a service `s` already in the ad cache, the registrar keeps one bound for the service
component. When a later request for `s` arrives, the charged service component is the larger of
the computed component and the bound's remaining value. The bound is dropped when the last
advertisement for `s` leaves the cache.

For IP addresses, lower-bound state is maintained at the IP-tree vertex corresponding to the longest
prefix match already present in the tree, without introducing new vertices only for pending
requests. The charged IP component is the larger of the computed component and the largest
remaining bound on any vertex along the address's path; reading the whole path keeps a bound
effective after later insertions create deeper vertices. If the advertisement has both an IPv4 and
an IPv6 address, the larger of the two path bounds applies. A bound disappears with its vertex when
the last address under that prefix leaves the tree.

## Advertiser Behaviour

### Advertisement Placement

For advertisement placement, the advertiser uses a compact table with 18 buckets. Logarithmic
distances `256` through `240` each have a separate bucket, while distances `239` and below share
the closest bucket. The buckets are indexed from `0`, the farthest, to `17`, the closest.

For each service `s` that a node advertises, the advertiser attempts to maintain up to `K_register`
active or pending registrations in each bucket of its advertise table `B(s)`. The current value is
`K_register = 10` (provisional, see [Parameters](#parameters)).

Each bucket holds its registrars in three states: **standby** candidates not yet contacted,
**waiting** registrars with an attempt in progress, and **registered** registrars holding an
admitted advertisement. Whenever fewer than `K_register` registrars of a bucket are waiting or
registered, a standby candidate becomes waiting and is contacted. A bucket keeps at most
`RegStandbyLimit` standby candidates; the recommended value is `RegStandbyLimit = 20`. A bucket with
fewer standby candidates than that has space, and its distance is listed in the topic-distance hints
of the advertiser's requests.

Candidate registrars come from the ordinary node table, filtered to TopDisc-capable nodes, and from
auxiliary ENRs. A candidate is not added to a bucket if:

1. it is the advertiser itself, or already in the bucket;
2. it is in the advertiser's failed set for `s` (see [Registration Procedure](#registration-procedure));
3. the bucket already holds `RegStandbyLimit` standby candidates;
4. another registrar in the bucket has an address in the same `/24` prefix. The current
   implementation applies this limit to the node's endpoint address, the more global of its IPv4
   and IPv6 addresses (IPv4 if both are equally global), with the same prefix length for both
   families. LAN addresses are exempt. The accounting lasts for as long as the service is
   advertised; or
5. the candidate is an auxiliary ENR, and the registrar that returned it has already contributed a
   candidate to that bucket, in this or an earlier response.

Advertisement placement is continuous soft state. Advertisers keep placing advertisements so that
they remain available despite expiry, churn, registrar failure, and changes in the service table.

The following rules are implementation guidance. They do not change what is sent in a single
registration request, but they decide whether ticket retries arrive within their window:

- The advertiser SHOULD send registration requests through several concurrent senders, so that a
  request to an unresponsive registrar does not hold back the others. The current implementation
  uses four senders per service.
- One bucket does not block another. When several buckets have a due attempt, the advertiser
  serves them in turn, one attempt per bucket, starting with the farthest bucket.
- Within a bucket, a due ticket retry goes before a first contact; otherwise the attempt due first
  goes first.
- The advertiser re-reads its ordinary node table at most once per `RegLoopMinPeriod` when it has
  no usable candidates; the recommended value is `RegLoopMinPeriod = 2 sec`.

### Registration Procedure

An advertiser registers an advertisement by sending a registration request to a selected registrar.
The corresponding wire-format request is specified in [REGTOPIC].

The first registration request for an advertisement is sent without a ticket. The registrar either
admits the advertisement immediately or returns a ticket and a waiting time in a [REGCONFIRMATION]
response, or rejects the request.

If the registrar returns a ticket, the advertiser waits for the given time and then retries with the
latest ticket, within the ticket's window. If the registrar still cannot admit the advertisement
after the retry, it returns an updated ticket and a new waiting time. The registrar may quote a
waiting time longer than `E`.

The protocol does not define a maximum total duration for a registration attempt. The advertiser
SHOULD abandon an attempt when a single quoted waiting time, or the sum of the waiting times quoted
in the attempt, exceeds the attempt budget `RegAttemptBudget`. The current value is
`RegAttemptBudget = 1.5 * E` (provisional, see [Parameters](#parameters)). After `E` all
advertisements in the registrar's cache have been replaced, so a registrar that has not admitted
the advertisement by then is overloaded or malfunctioning. An abandoned attempt does not place the
registrar in the failed set.

The advertiser MUST treat a quoted waiting time below `W_min` as `W_min`: it waits at least `W_min`
before retrying and keeps the registrar. The clamped value counts toward `RegAttemptBudget`. A
quoted value too large for the advertiser's duration type is saturated, and so exceeds the budget.
The lifetime in an admission is capped at `E`.

A registration attempt fails if the request times out, the registrar rejects the request, or it
returns a malformed response. On failure, the advertiser removes
the registrar from the bucket, fills the slot from the standby candidates, and adds the registrar to
its **failed set** for `s`. A registrar in the failed set is not added to the advertise table
again, from any source, for `E` from the time it was first added.

Only a timeout counts as a liveness failure of the registrar towards the ordinary node table. A
rejection is an answer: it shows that the registrar is reachable.

When registration succeeds, the advertisement remains stored by the registrar until it expires,
unless it is removed earlier by registrar policy. The advertiser takes the lifetime from the
`wait-time` of the [REGCONFIRMATION].

Registration responses may include auxiliary ENRs. The advertiser may use these ENRs to update
its advertise table `B(s)` after validating the ENRs, checking TopDisc capability, and applying
local usability policy. The recommended auxiliary-ENR selection rule is described in
[Auxiliary ENR Selection](#auxiliary-enr-selection). The current implementation accepts at most 8
auxiliary ENRs per registration request.

### Renewal

An admitted advertisement remains stored until its expiry time `E`. Because a registrar does not
refresh the expiry of an advertisement it already holds (see [Ad Cache](#ad-cache)), an
advertisement cannot be extended by registering again before it expires.

Renewal is therefore a new registration after expiry, not tied to the registrar that held the
advertisement. In the current implementation, when an advertisement expires, the registrar leaves
the bucket and the free slot goes to a standby candidate, which may be a different registrar. The
previous registrar becomes a candidate again only when it is offered again, from the node table or
as an auxiliary ENR. Until the new registration is admitted, the bucket holds one advertisement
fewer than `K_register`.

Advertisers should treat registrations as soft state. The target is not to permanently bind a
service to a fixed set of registrars, but to maintain sufficient active or pending placements across
the service-centred key space.

## Discoverer Behaviour

### Lookup Procedure

For lookup, the discoverer uses a compact search table with 18 buckets, ordered from farthest
to closest relative to `s`. Logarithmic distances `256` through `240` each have a separate
search bucket, while distances `239` and below share the closest search bucket. The search
buckets are indexed from `0` to `17`, where `0` is the farthest and `17` is the closest.

The discoverer maintains an active search bucket, which defines the current search region:
the service-distance region from which it currently prefers to select registrars for lookup.
At the start of a new lookup, the farthest search bucket, index `0`, is active. If it contains
no eligible registrar, the fallback rule below selects a registrar from another populated
search bucket without itself changing the active bucket. As responses are received, the discoverer updates the active bucket according to
the observed advertisement yield, i.e., the number of advertisement ENRs returned by queried
registrars: low yield moves the active bucket closer to `s`, sufficient yield keeps it at the
same distance, and consistently full responses move it farther from `s`.

A lookup runs as a sequence of search passes. Each pass fills a fresh search table from the
ordinary node table, starts at the active bucket chosen by the previous pass, and keeps its
own yield samples. The discoverer sends one query at a time. The rules below for pass length,
pass spacing, re-asking and result delivery are local policy: they do not change what is sent
for a single query, but they set how much load a discoverer places on registrars. The values
given are the recommended ones.

#### Registrar Selection

While a search pass remains active, each query first selects an eligible unqueried registrar from the active bucket. If none is available there, the discoverer considers neighbouring populated search buckets on either side of the active bucket, expanding outward one bucket at a time. When two candidate buckets are equally far from the active bucket, the bucket farther from `s` is considered first. The first bucket containing an eligible unqueried registrar is selected. Querying a registrar from such a fallback bucket does not itself change the active bucket. Therefore,
the bucket containing the queried registrar may differ from the active bucket. The fallback is only
a way to obtain another query target when the active bucket has no eligible registrar; the
search region (active bucket) changes only in response to observed advertisement yield.

Within a bucket, the discoverer SHOULD select the registrar pseudo-randomly, so that
discoverers of the same service do not converge on the same registrars.

The discoverer keeps two sets of registrars across the passes of a lookup. Each set holds a
registrar for `E` from the time it was first added; adding it again does not extend that time.

- The **asked set** holds registrars that answered a query. A registrar in the asked set is
  not an unqueried candidate in later passes.
- The **failed set** holds registrars whose query failed. A registrar in the failed set is
  not inserted into the search table, from any source, until it leaves the set.

A query fails when the registrar is unreachable, times out, or its response ends in an error
before any record (advertisement or auxiliary ENR) has arrived. A failed registrar is removed
from the search table. A response that ends in an error after some records have arrived is a
partial response; the registrar counts as having answered.

A registrar in the asked set that is offered to the search table again, from the node table
or as an auxiliary ENR, becomes a spare. When no search bucket holds an unqueried candidate,
the pass MAY re-ask one spare. The recommended choice is the spare whose last query is the
oldest, since its ad cache is the most likely to have changed. At most one spare is re-asked
per pass. A registrar that answered or failed during the current pass is not asked again in
that pass.

#### Advertisement Yield

For each complete response, the discoverer records one advertisement-yield sample for the
responding registrar's bucket. The sample is the number of advertisement records in the
[TOPICNODES] responses after per-record validation, the `F_return` size limit and
de-duplication by node ID within the response, and before the `ng` capability check and the
result filter described below. A complete response containing no advertisements contributes
a yield sample of `0`.

A partial response contributes a yield sample only if its count reaches `F` on its own. Its
count is a lower bound: it can show that yield is sufficient, but not that it is low. A failed
query contributes no yield sample.

During a search pass, each bucket retains its four most recent yield samples. A response does not change the active bucket until the responding bucket has at least two samples. Let `x` be those samples sorted in ascending order, and `m` their count, where `2 <= m <= 4`. With zero-based indexing and integer division:

    lower = x[(m - 1) / 2]
    upper = x[m / 2]

For odd `m`, `lower == upper` is the ordinary median. For even `m`, they are the two middle values
and are not averaged. Let `F = SearchYieldFloor`, the minimum advertisement yield considered sufficient to keep the
responding bucket as the active bucket for subsequent queries. The current value is `F = 8`.
`F_return = 16` is the maximum number of advertisement ENRs that a registrar may return in one
query response. For responding bucket index `b` and closest search-bucket index `last`, compute
the candidate bucket `next` as follows:

    if lower >= F_return:
        next = max(0, b - 1)
    else if upper >= F:
        next = b
    else if upper == 0:
        next = min(last, b + 4)
    else:
        jump = ceil(log2(F / upper))
        next = min(last, b + min(jump, 4))

The division in `F / upper` is real division. If the recent yield samples are consistently full (`lower >= F_return`), the search moves one
bucket farther from `s`. If the observed yield is sufficient but not consistently full
(`upper >= F`), the responding bucket is kept. If the yield is zero
(`upper == 0`), the search moves four buckets closer to `s`. Otherwise, when
`0 < upper < F`, it moves between one and four buckets closer, with lower yield causing a
larger move. All moves are limited to valid bucket indices.

The rule is evaluated on the samples of the responding registrar's bucket `b`, which differs
from the active bucket `a` when the query used a fallback registrar. The active bucket becomes
`next` only if one of the following holds:

1. `b` is at most `SearchAuxRadius` buckets from `a`;
2. `b` is farther from `s` than `a` (`b < a`) and `next <= b`; or
3. `b` is closer to `s` than `a` (`b > a`) and `next > b`.

Otherwise the sample is kept, but the active bucket does not change. Advertisement density
grows toward `s`, so a distant fallback bucket can only move the search in one direction:
sufficient yield farther out pulls the search out to that bucket or beyond, and low yield
closer in pushes it past that bucket. Low yield farther out, or sufficient yield closer in, is
what density alone predicts and does not move the active bucket.

#### Pass Transitions

A pass ends when no query is in flight, no result waits to be delivered, and one of the
following holds:

1. `SearchPassQueries` queries of the pass have completed, answered or failed (provisional,
   see [Parameters](#parameters));
2. the active bucket has no unqueried candidate and holds at least two yield samples; or
3. no search bucket holds an unqueried candidate and no spare can be re-asked.

The next pass starts at the active bucket if the pass ended by condition 1 or 2, or if a
yield sample changed or confirmed the active bucket during the pass. Otherwise the pass ran
out of candidates before the active bucket could decide, and the next pass starts one bucket
closer to `s`, unless the active bucket is already the closest bucket. Two exceptions apply:

- If the active bucket was queried during the pass, every query to it failed, and no yield
  sample placed it, the next pass retries the same bucket. Only one such retry pass is made;
  if it ends the same way, the following pass starts one bucket closer to `s`.
- If the pass started at the closest bucket, would start the next pass there as well, and
  received no advertisement from any registrar, the next pass starts at the farthest bucket,
  index `0`. This lets a lookup find the first advertisers of a service that had none.

Ending a pass does not end the overall lookup. The search continues with new passes, each starting
with fresh yield samples, until the caller closes the lookup or the discovery system shuts down.

Each pass starts at least `SearchPassGap` after the previous pass started. A pass is idle if
it delivered no result to the caller and either received no advertisements or leaves the next
pass starting at the same bucket as itself.
After `k` consecutive idle passes, the next pass starts at least
`min(SearchPassBackoff, SearchPassGap * 2^k)` after the previous one. A pass that is not idle
resets the spacing to `SearchPassGap`. The discoverer SHOULD back off this way; the
recommended values are `SearchPassGap = 2 sec` and `SearchPassBackoff = 60 sec`
(provisional, see [Parameters](#parameters)).

#### Result Delivery

A registrar returns advertisements for service `s` in [TOPICNODES] responses. The discoverer
validates the returned advertisements, discards those whose ENR does not advertise a supported
`ng` version, and extracts the advertised ENRs. Advertisements are candidate results for the target service. The caller may
stop lookup when it has collected enough distinct advertisers for its local or service-specific
purpose. This target is denoted `F_lookup` in this document and is determined by the application,
service binding, or local implementation policy. It is a caller-side result target, and has no protocol-wide fixed default. A caller stopping
before reaching its target retains the valid advertisers collected so far. The search iterator
continues through successive passes until the caller closes it or the discovery system shuts down.

The discoverer SHOULD NOT deliver the same advertiser repeatedly across passes. It records
each delivered node, with its ENR sequence number, in a result filter for `E` after the
delivery. While a node is recorded, it is not delivered again, except once with an ENR whose
sequence number is higher than the recorded one. After that re-delivery the node is not
delivered again until its entry expires. Within one pass, each node is delivered at most once.
The recommended filter capacity is `SearchFilterSize = 50,000` entries (provisional, see
[Parameters](#parameters)); when the filter is full, the entry that expires first is dropped.

The discoverer SHOULD mix results across registrars, so that the first results of a pass do
not all come from one registrar. Within a pass, results that pass the filter are queued per
responding registrar. Queued results are released once `SearchMixRegistrars` registrars have
replied with results in the pass, or once the first queued result has waited
`SearchMixWait`; the condition is checked whenever a query completes. Released results go out
in rounds, one result from each registrar with results waiting, in the order the registrars
first replied. A round with results from a single registrar waits until those results have
waited `SearchMixWait`. A node queued by several registrars is delivered once, with the ENR
that has the highest sequence number. When the pass ends, every queued result is released in
the same rounds. The recommended values are `SearchMixRegistrars = 5` and
`SearchMixWait = 5 sec` (provisional, see [Parameters](#parameters)).

The discoverer SHOULD NOT send a new query while `SearchUnreadLimit` or more results wait
unread by the caller, and resumes querying when the caller reads. The recommended value is
`SearchUnreadLimit = 16`, equal to `F_return` (provisional, see [Parameters](#parameters)).

Lookup responses may also include auxiliary ENRs in [NODES] responses. These ENRs are not lookup
results; they are auxiliary routing information used to improve the discoverer's search table
`B(s)`. The recommended auxiliary-ENR selection rule is described in [Auxiliary ENR
Selection](#auxiliary-enr-selection).

### Lookup Responses

A registrar receiving a lookup request for service `s` returns advertisements for that service from
its ad cache. A registrar receiving a [TOPICQUERY] request for service `s` returns advertisements
and auxiliary ENRs using the response format defined for `TOPICQUERY` in the wire specification.

The registrar MUST NOT return expired advertisements. If more than `F_return` advertisements for the
service are present in its ad cache, the registrar SHOULD return a pseudo-random subset of at most
`F_return` advertisements. The selection procedure SHOULD avoid deterministic bias towards the same
advertisers across repeated lookup requests.

A registrar may also return auxiliary ENRs selected according to
[Auxiliary ENR Selection](#auxiliary-enr-selection). These ENRs are not lookup results; they are
auxiliary routing information used to improve future registration and lookup operations.

The requester uses returned auxiliary ENRs to update its local service table `B(s)` after validating
the ENRs, checking TopDisc capability, and applying local usability policy. The exact
encoding of returned advertisements, auxiliary ENRs, and any topic-distance list is specified in the
wire-format document.

### Updating the Search Table During Lookup

The discoverer updates `B(s)` using auxiliary ENRs returned in [NODES] responses to lookup requests.
These ENRs are registrar candidates for the search table, not advertisement lookup results.

During adaptive lookup, [TOPICQUERY] requests auxiliary candidates for topic-distances corresponding
to search buckets around the current active bucket. `SearchAuxRadius` controls this neighbourhood;
its current value is `1`. The request therefore normally includes the active bucket and its
neighbouring search buckets, subject to valid indices and available capacity. A bucket has space
when it holds fewer than `SearchBucketSize` candidates. This replenishes registrar candidates in
the service-distance region that adaptive lookup currently prefers. The discoverer lists the
topic-distances from farthest to closest to `s`. A registrar that caps auxiliary ENRs serves
the earliest listed distances first (see [Auxiliary ENR Selection](#auxiliary-enr-selection)).

An ENR learned through lookup is eligible for insertion into the search table only if:

1. the ENR is valid;
2. the ENR advertises a supported TopDisc version;
3. the node is not temporarily excluded by local TopDisc usability policy, and is not in the
lookup's failed set;
4. the advertised IP address passes the ordinary Discovery v5 address-validation checks and any
configured network restrictions;
5. the ENR advertises a UDP port greater than `1024`;
6. the node is not the discoverer itself or a duplicate candidate, has not answered or failed
a query in the current pass, and is not in the lookup's asked set (such a node becomes a
spare, see [Lookup Procedure](#lookup-procedure));
7. the destination search bucket has available capacity; and
8. inserting the node does not violate the bucket's IP-prefix diversity restriction.

As part of the IP-prefix diversity restriction, the current implementation allows at most one
candidate from the same `/24` prefix in a search bucket; LAN addresses are exempt from this
restriction. As in the advertise table, the limit applies to the node's endpoint address, IPv4 or
IPv6, with the same prefix length for both families. The search table is filled
afresh for each pass, so the restriction holds within one pass. A registrar that answered keeps
its prefix slot for the rest of the pass, so another node from the same `/24` cannot take its
place; a registrar whose query failed releases its slot. This differs from the advertise table,
which keeps its prefix accounting for as long as the service is advertised.

When processing auxiliary ENRs from a single response, at most one candidate is admitted into
any given search bucket. This limits the contribution of a single responding registrar to that
bucket within one response.

A successful ordinary Discovery v5 liveness check is not required before insertion. If the node
subsequently fails to respond to a TopDisc request, it may be removed or temporarily excluded
according to the TopDisc failure-handling rules.

## Implementation Considerations

### ENR Freshness

Advertisers should send their current ENR when registering an advertisement.

Registrars should store the ENR that was admitted and return that ENR in lookup responses until the
advertisement expires or is renewed.

### Clocks

TopDisc does not require clock synchronisation between advertisers and registrars.

Tickets carry registrar-generated timing information. Advertisers only need to wait for the duration
indicated by the registrar before retrying.

### Response Splitting

TopDisc responses may be split across multiple packets when supported by the wire protocol.

Implementations should collect all response packets belonging to the same request until the
announced response count is reached or the request times out.

### Wire Encoding

This document describes algorithms and data structures.

The exact encoding of TopDisc messages, ticket signatures, request identifiers, response splitting,
returned advertisements, neighbour ENRs, and any application-specific advertisement payload is
specified in the wire-format document.
